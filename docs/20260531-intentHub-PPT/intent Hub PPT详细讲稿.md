## 1. 封面：Intent Hub

各位好，今天介绍的是 Intent Hub。

它的副标题是“让 AI 能力找到正确入口”。这句话其实就是整个产品的核心。过去我们谈 AI 应用，往往重点放在模型本身：模型能不能理解、能不能生成、能不能推理。但当一个系统真的进入日常使用后，问题会变得更具体：用户说了一句话，系统到底应该调用哪个 Skill、哪个 Agent、哪个内部工具，或者进入哪条工作流？

Intent Hub 想解决的就是这个中间层问题。它不是要替代 Agent，也不是要替代具体工具，而是站在用户输入和能力执行之间，做一件很关键的事情：理解意图，并把意图路由到正确的能力入口。

所以今天这份介绍会沿着一个产品叙事展开：为什么能力多了以后需要路由，Intent Hub 在系统里处在什么位置，它提供哪些核心能力，开发者、团队和平台分别怎么使用它，以及它最终能给 AI 应用带来什么价值。

这一页只需要记住一个关键词：Intent Hub 是 AI 应用里的能力选择层。

## 2. 背景：AI 能力变多之后，入口开始失控

我们先看一个很现实的变化。

现在的 AI 系统已经很少只是“一个聊天框加一个模型”。一个稍微完整一点的 AI 产品，往往会接入很多能力：文档处理、网页浏览、知识库整理、代码任务、数据分析、内容生成、自动化工作流，甚至还有很多专用 Agent 和 Skill。

这些能力本身是好事，说明系统越来越强。但能力越多，另一个问题就会出现：用户并不想先学习这些能力叫什么、分别适合什么场景、应该用什么触发方式。用户通常只会说一句自然语言，比如“帮我整理这批资料并生成结构化文档”。这句话背后可能涉及知识库整理、文档生成、内容改写，甚至还可能需要读取网页或项目文件。

如果系统让用户自己选工具，体验会变重。如果让每个 Agent 自己在 prompt 里判断，逻辑会越来越分散。如果写在业务代码里，又会让能力新增和调整变得很难维护。

所以，AI 产品的复杂度正在从“模型有没有能力”，转移到“系统如何选择能力”。这就是这一页下方那句话：The new problem is routing。

## 3. 产品定位：Intent Hub 是 AI 能力的路由中枢

基于刚才的问题，我们来看 Intent Hub 的定位。

Intent Hub 可以理解为一个统一的意图路由中枢。它接收用户或 Agent 提交的自然语言任务，然后根据已有的能力描述、路由配置和索引，判断最匹配的能力，最后返回 route key、匹配结果或 dispatch 建议。

这里有三个关键动作。

第一，接收意图。输入不要求是结构化命令，可以是一句自然语言，比如“帮我整理 wiki”。

第二，判断方向。Intent Hub 会把这句话和系统里已经配置好的 routes、utterances、Skill 描述以及索引结果进行匹配。

第三，返回建议。它不会直接替上层应用把所有事情都执行完，而是告诉上层系统：这件事更像应该交给哪个能力处理。

这也是它和 Agent 的边界。Agent 更像执行者，负责把任务真正做完；Intent Hub 更像路由层，负责在执行开始前判断方向。它不替代 Agent，而是帮助 Agent 找到正确入口。

## 4. 产品价值：把“能力选择”产品化

如果没有 Intent Hub，能力选择通常会藏在很多地方。

有些藏在 prompt 里，比如告诉模型“如果用户说整理资料，就调用某某工具”。有些藏在业务代码里，比如写一堆 if else 或规则判断。有些藏在人工说明里，靠用户自己记住该用什么工具。还有些藏在每个 Agent 自己的逻辑里，导致同一类任务在不同地方判断标准不一致。

这些方式一开始都能工作，但随着能力数量增加，会出现几个问题：入口不统一、规则不可见、测试困难、优化困难，也很难沉淀成团队资产。

Intent Hub 的价值，是把“能力选择”这件事从隐藏逻辑里抽出来，变成一个独立、可管理、可测试、可优化的产品能力。

统一入口，意味着用户只需要表达任务，不需要知道工具名。

能力沉淀，意味着 Skill 可以被扫描、导入和维护，而不是只存在于个人目录或项目角落。

可测试，意味着我们可以明确验证一条输入到底会命中哪个 route。

可优化，意味着当命中效果不好时，可以通过诊断、样本和索引同步继续改进。

所以这一页的核心判断是：能力选择本身，需要被产品化。

## 5. 产品总览：Intent Hub 的能力地图

这一页是整套产品能力的总览。

Intent Hub 不是单一的“预测接口”，而是一套围绕能力路由展开的工作台。它可以分成五类核心能力。

第一类是意图路由。也就是把自然语言输入匹配到合适的能力，这是最核心的运行时能力，对应当前主接口里的 `/v1/route` 和 `/v1/dispatch`。

第二类是 Skill 管理。很多团队已经有本地 Skill 或 Agent 能力，Intent Hub 支持通过 Web、CLI 或 SDK 收集 `SKILL.md` 内容，并上传到后端生成或更新路由实体。

第三类是路由测试。团队可以拿一条真实输入去验证会命中哪个 route，这让能力选择从“感觉上应该可以”变成可以被检查的结果。

第四类是诊断优化。随着 route 变多，能力之间会有重叠、误命中或索引不同步，Intent Hub 提供诊断、修复和同步相关接口来维护质量。

第五类是集成接入。不同角色可以用不同入口：产品和运营用 Web 管理台，开发者用 CLI 和 Python SDK，上层 Agent Runtime 则可以直接接入 HTTP API。

后面的页面会分别展开这些能力。

## 6. 核心能力一：意图路由

我们先看最核心的能力：意图路由。

用户输入往往不是结构化命令，而是自然语言。比如“帮我整理 wiki”、“测试一下这个网页”、“把这篇文章改得不像 AI 写的”、“根据这些资料生成项目介绍”。这些表达对用户来说很自然，但对系统来说，需要先判断它们分别属于哪类能力。

Intent Hub 的运行时接口就是为这个场景设计的。当前主要有三个租户运行时接口：`/v1/me`、`/v1/route` 和 `/v1/dispatch`。

`/v1/me` 用来确认当前 access code 对应的租户身份。`/v1/route` 用来做路由判定，返回匹配到的 route 信息。`/v1/dispatch` 则进一步返回 dispatch 建议。这里需要特别说明：当前 dispatch 返回的是建议，不会直接执行外部工具。也就是说，它负责告诉上层“应该往哪里走”，真正执行仍然由 Agent Runtime 或业务系统完成。

这种边界很重要。Intent Hub 降低的是“选择能力”的成本，而不是把所有能力执行都塞进一个系统里。这样设计以后，上层应用可以保持灵活，路由层也可以独立测试和优化。

## 7. 核心能力二：Skill 扫描与导入

第二个核心能力是 Skill 扫描与导入。

很多团队已经有自己的 Skills、脚本或 Agent 能力。这些能力通常以目录、Markdown 说明或项目文档的形式存在，比如每个 Skill 目录下有一个 `SKILL.md`。问题是，这些能力虽然存在，但并不一定能被系统统一发现和路由。

Intent Hub 的做法是把这些分散的 Skill 收进统一目录。当前设计里，Skill 扫描已经明确改成客户端本地目录模式。也就是说，CLI、Python SDK 或 Web 页面先在用户本机读取 `SKILL.md`，再把内容上传到后端。后端不再假设普通租户可以直接指定部署机器上的目录去扫描。

这个设计有两个好处。

第一，它更符合真实使用场景。Skill 往往在用户自己的电脑、团队仓库或本地工作区里，而不一定在服务器上。

第二，它更安全也更清晰。后端保存的是 Skill source 的逻辑元数据和上传内容，不需要直接访问用户机器上的文件路径。

上传后，系统会根据 Skill 内容生成或更新路由草稿，并维护 `skills_index.json`。当 route 同步到索引后，这些 Skill 就从“本地文件”变成了“可被路由的能力”。

这就是这一页的核心：让分散的 Skill 进入统一目录。

## 8. 核心能力三：Web 管理台

第三个能力是 Web 管理台。

Intent Hub 不只是一个后台接口。它也提供 Vue 管理前端，让路由能力变成可以被看见、被维护、被运营的产品对象。

从当前项目结构看，前端在 `intent-hub-frontend/`，后端是 Flask 服务，前端通过 API 调用后端。管理台面向的不是单一开发动作，而是一整套能力运营流程：查看和维护 routes、测试输入命中结果、管理 Skill 来源、处理导入草稿、查看诊断结果、调整配置并同步索引。

这一点对团队协作很关键。因为在真实团队里，维护 AI 能力的人不一定只有后端开发。产品、运营、Agent 设计者、平台维护者，都可能需要知道当前有哪些能力、哪些能力可以被命中、哪些能力描述需要调整。

如果这些信息只藏在代码和配置文件里，协作成本会很高。Web 管理台的价值，就是把能力路由从“工程内部逻辑”提升成“团队可协作维护的产品对象”。

所以这一页可以强调三个词：Manage、Test、Improve。管理能力、测试命中、持续改进。

## 9. 核心能力四：CLI / SDK 接入

第四个能力是 CLI 和 SDK 接入。

Web 管理台适合可视化管理，但开发者、自动化脚本和 Agent Runtime 往往需要更轻量的接入方式。所以仓库里把 `intent-hub-cli/` 做成了独立分发包，包名是 `intent-hub-cli`，当前文档中的安装方式是 `pip install intent-hub-cli==0.1.4`。

安装后，开发者可以用 `intent-hub` 或 `intenthub` 命令访问远程服务。常见动作包括登录、确认身份、测试路由、扫描本地 Skill、同步索引。

比如：

```bash
intent-hub route "帮我整理 wiki"
intent-hub skills scan --source-path ./skills
intent-hub sync
```

如果在 Python 代码里接入，也可以直接使用 SDK：

```python
from intent_hub_cli import IntentHubClient

client = IntentHubClient(endpoint="https://api.example.com", access_code="<access_code>")
print(client.route("帮我整理 wiki"))
```

这里的产品意义是：Intent Hub 不是只能人在网页里点，它也能进入开发者工作流。Web 管理台负责配置和运营，CLI/SDK 负责自动化和集成，上层系统则可以通过 API 在运行时调用。

## 10. 核心能力五：诊断与优化

第五个能力是诊断与优化。

意图路由不是一次配置后就永远正确。随着能力越来越多，系统会遇到很多质量问题。比如两个能力描述很相似，用户输入和样本表达不一致，新增 Skill 后没有及时同步索引，某些 route 容易误命中，或者能力边界本身就不够清楚。

所以 Intent Hub 需要的不只是“能路由”，还需要一个质量闭环。

当前 API 里已经有诊断相关接口，例如 overlap 诊断、repair、apply-repair、umap，以及 reindex 和 sync-route。这些接口对应的产品动作可以理解为：先测试，再诊断，再修复，再同步，最后回到路由验证。

这页中间那句话很关键：Routing quality is an operating loop。路由质量不是一个静态结果，而是一个持续运营过程。

当团队新增能力、修改 Skill 描述、调整 route 样本或者发现误命中时，都应该回到这个闭环里：验证问题，定位原因，修复配置，同步索引，再观察路由效果。

这也是 Intent Hub 从“接口工具”变成“产品工作台”的关键差异。

## 11. 使用路径：一次完整的产品体验

这一页把前面的能力串成一次完整体验。

一个典型路径可以这样理解。

第一步，团队准备一组 Skills。这些 Skills 可能来自个人经验、团队仓库，也可能是已经在 Agent 系统里使用的能力说明。

第二步，通过 Web、CLI 或 SDK 扫描这些 Skills。扫描的重点不是让后端去读用户电脑，而是由客户端收集本地 `SKILL.md`，再把内容上传。

第三步，Intent Hub 根据 Skill 内容生成或更新 route。这里 route 会包含名称、route key、描述、样本 utterances 等信息。

第四步，执行索引同步。因为路由配置变化后，只有同步到索引层，运行时匹配才能使用最新能力。

第五步，用户提交自然语言任务，比如“帮我整理 wiki”。

第六步，Intent Hub 返回匹配结果或 dispatch 建议。

第七步，Agent 或上层应用根据这个建议继续执行真正的任务。

这条路径说明，Intent Hub 覆盖的是从“能力进入系统”到“用户请求命中能力”的完整链路，而不只是某一个 isolated API。

## 12. 应用场景一：团队 Skill 能力库

第一个典型场景，是团队共享 Skill 能力库。

很多团队在使用 AI 工具一段时间后，会沉淀大量 Skills：文档整理、知识库构建、网页分析、代码审查、内容改写、PPT 生成、数据处理等等。问题是，这些能力经常散落在不同人的本地目录、不同项目仓库、不同说明文档里。

结果就是，能力虽然存在，但使用门槛很高。新成员不知道有哪些 Skill，老成员也不一定记得每个 Skill 的准确触发方式。很多能力最后变成“只有作者知道怎么用”的个人经验。

使用 Intent Hub 后，团队可以把这些 Skills 纳入统一目录。用户不再需要先记住工具名，而是直接表达任务。系统根据 Skill 描述和 route 样本判断应该命中哪个能力。

这会带来三个变化。

第一，团队内部使用门槛降低。

第二，能力不再依赖个人记忆，而是进入可维护的系统。

第三，分散经验可以沉淀为团队资产。

所以这一页底部的英文可以翻译成：从分散的技能，到共享的能力。更适合产品标语的说法是：让分散的 Skill，成为团队共享能力。

## 13. 应用场景二：Agent 产品的前置路由层

第二个场景，是给 Agent 产品加一层前置路由。

在 Agent 产品中，用户输入可能对应完全不同的处理链路。比如查询资料、浏览网页、处理文档、修改代码、调用内部工具、生成内容、执行自动化流程。这些判断如果全部写在 Agent prompt 里，prompt 会越来越长，也越来越难维护。如果写在业务代码里，新增能力时又需要频繁改代码。

Intent Hub 可以放在 Agent Runtime 前面。用户输入先进入 Intent Hub，Intent Hub 返回 route 或 dispatch 建议，然后 Agent Runtime 根据建议选择后续执行链路。

这里的关键价值不是“多调用了一层服务”，而是把能力判断从 Agent 自身解耦出来。这样能力新增、能力调整、路由测试、质量诊断，都可以在 Intent Hub 里独立进行。

对 Agent 产品来说，这会让前置判断更轻，系统边界更清楚。Agent 继续负责执行，Intent Hub 负责选择方向。两者组合起来，会比把所有判断都塞进一个 prompt 或一段业务代码里更容易演进。

## 14. 应用场景三：AI 平台的能力运营后台

第三个场景，是 AI 平台的能力运营后台。

当一个平台接入的 AI 能力越来越多时，真正重要的不只是“我们有多少能力”，还包括这些能力的生命周期管理。

比如，哪些能力已经上线？哪些能力可以被路由命中？哪些能力命中不稳定？哪些能力描述需要更新？哪些能力之间存在重叠？哪些能力长期没有被使用？这些问题如果没有统一后台，就很容易散落在代码、文档、聊天记录和个人经验里。

Intent Hub 可以作为 AI 能力运营后台的一部分，把 Skills、Routes、Drafts、Diagnostics、Sync Status 这些对象放到同一套体系里。

从架构上看，后端已经按多租户模型组织运行时数据。平台层保存租户和管理员设置，租户层保存 routes、settings、diagnostics cache、skills index 和 imports。这个结构说明，Intent Hub 不是只面向单个 demo，而是面向多团队、多租户、多能力集合的使用方式。

所以这一页的核心价值是：让 AI 平台从“工具集合”升级为“能力体系”。工具集合强调有多少工具，能力体系强调这些工具能否被发现、被路由、被维护、被优化。

## 15. 总结：Intent Hub 的核心价值

最后我们收束一下。

Intent Hub 的核心价值可以用三句话概括。

第一，对用户来说，不用记工具名，只需要表达任务。用户关心的是“我要完成什么”，而不是“我应该先打开哪个 Skill”。

第二，对 Agent 来说，不用写死复杂判断，可以获得统一路由建议。Agent 可以更专注于执行，而不是把大量能力选择逻辑混在 prompt 或业务代码里。

第三，对团队来说，能力可以被扫描、测试、诊断和持续优化。团队沉淀下来的 Skills 不再只是分散文件，而是可以进入统一目录，变成可运营资产。

所以 Intent Hub 的最终定位是：AI 应用中的 Capability Routing Layer，也就是能力选择层。

如果说模型解决的是“能不能理解和生成”，Agent 解决的是“能不能执行任务”，那么 Intent Hub 解决的是中间这个越来越重要的问题：面对越来越多的 AI 能力，系统如何找到正确入口。

这就是 Intent Hub 想提供的产品价值：让 AI 能力可发现、可路由、可运营。

## 备用问答

### Q1：Intent Hub 会直接执行工具吗？

当前设计里，`/v1/dispatch` 返回的是 dispatch 建议，不直接执行真实工具。真正执行仍然交给 Agent Runtime 或上层业务系统。这样可以保持路由层边界清晰。

### Q2：为什么 Skill 扫描要放在客户端？

因为用户的 Skill 通常在本地目录或团队仓库里，不一定在后端部署机器上。当前设计是 CLI、SDK 或 Web 端先读取本地 `SKILL.md`，再上传内容到后端，后端维护 Skill index 和 route 草稿。

### Q3：Web、CLI、SDK 分别适合谁？

Web 适合产品、运营和团队维护者做可视化管理；CLI 适合开发者在终端和自动化脚本中使用；Python SDK 适合 Agent Runtime 或业务系统直接集成。

### Q4：Intent Hub 和 Agent 的关系是什么？

Intent Hub 是 Agent 前面的能力选择层。它负责判断任务方向，Agent 负责继续执行任务。它不是替代 Agent，而是让 Agent 少承担一部分分散且难维护的前置判断。

### Q5：多租户在产品里意味着什么？

多租户意味着不同团队可以有自己的 access code、routes、settings、skills index 和 diagnostics 数据。平台管理员管理租户，租户通过 `/v1/*` 和 `/tenant/*` 使用自己的能力路由体系。
