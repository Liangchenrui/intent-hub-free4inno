## 3. 第 3 页：流程对齐

### 3.1 保留的行为

1. 先进行常规例句检索，应用阈值、负例排除、生命周期和请求范围约束。
2. 有合格结果则直接返回；无结果且开启 LLM 兜底才进入模型判断。
3. 模型只能选择候选中的有效实体；无适用候选或存在歧义时允许返回空列表。
4. 命中后重新校验实体，允许自动学习时去重保存请求原文，并异步同步向量。
5. 自动学习写入失败不取消本次合法匹配；队列失败依靠既有 outbox 保留待同步工作。返回匹配不等于例句已成功入库或向量已同步。

### 3.2 R2 已选择 Top-K（保留对照方案）

| 方案 | 具体行为 | 对需求的影响 |
| --- | --- | --- |
| 保留 Top-K | 按当前查询范围召回描述 Top-K，再交给模型判断 | 改动较小；PPT 的“全部智能体”必须改为“召回的候选智能体” |
| 全量候选 | 当前查询范围内全部符合资格的智能体参与模型判断 | 才能对齐“全量”目标；需定义上下文超限处理并验证时延、成本与漏选情况 |

不能把“调大 K”直接等同于全量。全量方案仍需定义生命周期、负例排除、指定上游和 collection 的边界；不能为了全量而跨越调用方指定范围。若上下文放不下，必须明确分批或失败策略，不能静默截断后仍称全量。

验收：普通命中不调用 LLM；无匹配、歧义、非法 ID、服务异常不学习；重复请求不重复追加；实体并发变更不错误学习；测试界面关闭自动学习；按选定策略核对实际送入模型的候选集合。

## 4. 第 4 页：同步规则

### 4.1 S1：稳定身份

- 现有 `route_key` 为“上游命名空间.编码后的资源 ID”；内部实体 ID、外部资源 ID、显示名称保持各自语义。
- 应用改名仍更新原实体；不同上游的相同资源 ID 不冲突；同名而资源 ID 不同的应用不合并。
- 若“来源方向”指应用详情中的 `source` 字段，而非配置中的上游命名空间，则需要另行定义映射及迁移；不自行重建现有身份。

### 4.2 S2：上游例句与本地例句

PPT 明确要求新建时不读取上游例句；没有明确说明旧应用后续更新是否也应忽略，以及是否包括负例。

已选择并实现：应用中心提供应用信息，Intent Hub 维护正、负例句。

- 新同步的应用正、负例句为空，后续由管理员维护或已有自动学习机制补充。
- 后续拉取不覆盖本地正、负例句；现有例句和自动学习来源记录保留，不做历史清空。
- 上游例句为空、缺失或格式错误不应阻塞应用信息同步。
- 不能只把解析结果设为空：需要同步调整合并、受托管字段、比较及“恢复上游字段”入口，防止清空本地例句或重新导入上游例句。
- 上游例句单独变化不触发应用更新提醒。
- 原始响应可能仍含 `extent00` / `extent01`。是否保留在 `details` 中供兼容接口返回需核对接口契约；即使保留，也不作为本地路由语料和提醒依据。若“不读取”要求连原始详情也排除，需另列兼容变更。

验收：首次同步不导入语料；重复同步保留本地语料；上游语料变化及格式异常不影响应用同步；自动学习语料保留；恢复字段操作不能绕过新规则；空例句应用仍可按选定的描述兜底策略参与匹配。

### 4.3 S3：按差异更新

- 对规范化后的业务字段比较；无实质变化不写实体、不触发索引、不新增提醒。任务记录和来源级拉取时间可以更新。
- 名称、描述等影响路由的有效变化继续触发已有后台增量索引。
- 详情变化按业务字段确定更新和提醒，排除拉取时间、访问统计等非业务噪声；实施前根据实际应用中心契约列出字段清单。
- 建议保留现有人工覆盖保护：上游变化更新基线，人工覆盖字段保留本地值，并提醒管理员处理。
- 若要求完全按上游覆盖，应只对明确归上游管理的字段执行，不能连同本地例句和管理员状态一起覆盖。
- 保留不完整列表、详情失败、空返回的保护；不能将查询失败解释为应用删除。

验收：无变化不写实体与 outbox；覆盖字段变化仍可产生提醒；无关详情噪声不反复提醒；部分失败保留原实体；下架、恢复的提醒策略单独配置规则或明确暂不纳入。

## 5. N1–N4：管理员待处理功能

### 5.1 状态语义与触发

建议字段名 `needs_review`，界面文案“待处理／已处理”。TRUE 表示管理员需要检查或维护，FALSE 表示已确认；它不代表向量同步状态，也不控制智能体是否可参与路由。

| 事件 | 建议行为 |
| --- | --- |
| 同步新增智能体 | 置为待处理，原因“新增” |
| 上游业务信息发生变化 | 置为待处理，记录变化字段 |
| 上游变化被本地人工覆盖挡住 | 仍置为待处理，提示保留人工修改 |
| 重复拉取且未变化 | 保持原状态，不自动清除 |
| 打开详情或保存例句 | 不自动清除，避免把查看或未完成编辑当成确认 |
| 点击“标记已处理” | 校验版本后置为已处理 |
| 点击“重新标记待处理” | 置为待处理，记录人工操作原因 |
| LLM 自动增加例句、索引完成或重试 | 不触发这一类上游更新提醒 |
| 手动新增、导入、下架、恢复 | PPT 边界不完整；第一版建议聚焦上游新增／更新，其余按需扩展 |

### 5.2 页面和接口

- 列表：显示待处理状态；建议增加待处理数量、筛选，配合现有搜索定位应用。数量与筛选口径必须一致，不以当前页条数代替总数。
- 详情：显示状态、变化时间、变化原因／字段；提供两个明确动作，而非语义不明的 TRUE/FALSE 开关。
- 同步结果：保留本次任务统计；“本次新增／更新数量”与“累计待处理数量”分别展示，不能互相替代。
- 建议新增管理接口 `PATCH /routes/{id}/review`，接收目标状态和详情页读取的状态版本，沿用管理鉴权。路径为设计建议，实施时纳入现有 API 契约及前端适配。
- 第一版建议共享处理状态：一个管理员确认后，全局变为已处理。每位管理员独立已读、批量确认和通知推送不属于最小范围。

### 5.3 数据与并发

建议在 `RouteConfig` 中增加独立 `review` 元数据，保存待处理布尔值、状态版本、变化时间、原因及变化字段。现有 SQLite 的 `entities.body` 可保存该结构；如后续需要数据库级筛选索引，再评估独立列或表。

- 状态版本在业务更新和人工状态改变时递增，不复用向量同步版本。
- 上游合并和提醒更新在同一 SQLite 事务中提交，避免只更新应用却漏掉提醒。
- 确认时比较客户端所见版本；若管理员查看期间再次更新，则返回冲突并提示刷新，不清除新提醒。
- 专用状态接口事务内读取最新实体，只改提醒字段；普通编辑、旧客户端、后台同步和导入路径不得用旧对象覆盖最新提醒。
- 状态修改不调用路由变更标记，不创建 outbox；提醒字段排除在路由 hash、`delta_sync.business_snapshot` 等索引变更判断之外。不能只改一个 hash 函数。
- 向量库不是提醒状态的事实来源；索引恢复或旧备份导入不得无意覆盖已有本地处理状态。
- 第一版旧实体建议默认已处理，新规则生效后新建／更新再提醒；不要把所有历史数据伪装成“刚更新”。如需首次全量检查，另行选择一次性标记待处理。

### 5.4 “哪些更新了”与“具体改了什么”

最小版实现：定位哪些智能体待处理，显示变化字段，管理员完成维护后确认。

增强版按需增加：相对上次确认的字段前后值。现有 `source_snapshot` 只保存最新上游信息，现有 diff 比较的是“本地与最新上游”，不能提供历史变化。要显示历史差异，需要额外保存已确认基线或变更记录；连续多次更新不能只保留最后一次差异而漏掉尚未处理的变化。
