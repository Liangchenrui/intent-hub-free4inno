# 低时延增量同步修复

## 目标与设计

2026-09-18：按用户要求设计并实现。当前问题是保存未变化的设置也重建全部路由、单条任务绕过增量判断，以及无变化同步重复写元数据。

- 设置保存比较生效前后的实际值。依赖参数变化才重置组件；模型、目标库、Embedding 地址或协议变化排入增量检查，不直接重建全部路由。只改地址但模型标识相同时允许复用向量。
- 单条任务和手动增量同步共享差异引擎。元数据保存完整路由快照及提交标记；忽略运行状态与更新时间比较业务内容。
- 已提交且业务内容相同的路由不编码、不写远端。变化路由读取其现有点，复用同模型同文本的有效向量；仅编码缺失文本。阈值变化只写 payload。
- 编码完成后再写向量及删除过期点，最后提交元数据。写入前使旧提交标记失效，失败不能被下一次无变化判断误认为成功。版本确认仍使用 compare-and-set。
- 日常全库增量检查优先扫描路由元数据并核对点数；旧库或数量不一致回退完整扫描。显式全量重建保留完整校验。
- 保留单写者及任务合并，正例、负例、描述的缺失文本在单路由内去重并批量编码；跨路由仍串行。不引入全局向量缓存或无界并发。
- 无变化任务不触发诊断；实际变更的诊断刷新需求保留至队列空闲，即使队列最后一项是无变化任务也会刷新。
- 添加 `queue_wait_ms`、`execution_ms`、`lock_wait_ms`，以及路由的读取/规划、编码、写入分段计时。执行时间包含锁等待；重试的排队时间从上次重新入队起算，包含退避时间。模型名称作为向量版本标识，实际模型变化必须更新该标识。

## 验收

重复设置保存无任务；重复同步零编码零写入；阈值变更零编码；修改一条例句仅编码新文本；删除仅删除过期点；模型变更全部编码；描述旧零向量补齐；失败重试与并发版本保护。

## 验证证据

环境：2026-09-18，Windows/PowerShell，本机 Python，临时 SQLite 和 Qdrant 内存实例，Embedding 为确定性测试替身；没有调用生产向量库进行重建。

修复前新增的三个回归用例均失败，分别捕获未变化路由仍删除重建、阈值修改仍编码、单个文本变化仍全路由编码。修复后均通过。

| 场景 | 观察结果 |
| --- | --- |
| 8 路由、90 正例、无负例，完成初次索引后再次全库增量同步 | 1 次元数据 scroll + 1 次 count；0 次 retrieve；0 次 upsert/set_payload/delete；0 次编码 |
| 单条无变化同步与后台无变化任务 | 0 次编码、0 次远端写入、后台不触发诊断 |
| 阈值修改 | 正负例阈值正确更新，0 次编码 |
| 替换一个正例 | 仅编码替换后的文本，旧点删除，其他文本保留 |
| 修改描述 / 模型名称 | 分别只编码描述 / 编码所有所需文本 |
| 编码失败、部分写入失败后恢复旧内容 | 编码失败保留旧索引；部分写入令提交标记失效，重试可正确清理多余点 |
| 编码期间出现新版本 | 不确认新版本已同步，后续同步可完成最新版本 |
| 删除一个向量点后增量检查 | 数量不符触发校验与补齐，只编码缺失文本 |
| 元数据旧格式或缺失 | 补齐后下一次可直接跳过 |
| 设置重复提交 / LLM 设置修改 | 不重置向量组件、不新增同步任务 |

上述无变化 8 路由场景，旧实现按代码需 18 次 Qdrant 请求（2 次全点扫描 + 8 次向量读取 + 8 次元数据写入）；新实现用请求计数测试实测为 2 次读取。**这是请求数量对比，不是远端时延提速倍数。** 不包括冷启动组件维度探测；旧库首次同步需要一次升级检查。

## 运行与限制

实现和必要验证已完成，文档 8 个相对链接及 5 个修改模块的 Python 语法检查通过。未执行生产部署或远端压测；真实服务的 p50/p95 延迟尚未测量，不能承诺固定毫秒级 SLA。

- 默认普通同步即可逐步升级旧元数据，无需清库。显式全量重建保持原行为。
- 元数据提交标记依赖本服务作为索引写入者。外部修改若同时保持总点数与提交记录不变，快速检查无法证明逐点完整性，应使用显式重建恢复。
- 无变化任务只更新本地任务状态；远端恢复记录保留上次内容写入时的任务 ID、时间与版本，不用于判断当前后台任务是否完成。
- 更换实际模型必须更新 `EMBEDDING_MODEL_NAME`。不同向量维度仍需适配目标 Collection。
- 同步与设置仍共享现有写入锁；真实新文本延迟受 Embedding、Qdrant、排队及锁等待影响，新增计时字段用于进一步定位。
